# Docker

Docker configuration for the Nvisy server.

## Infrastructure Requirements

Nvisy requires three external services:

**PostgreSQL 18+**. PostgreSQL serves as the primary data store for all
application state: accounts, workspaces, documents, connections, and file
metadata. It uses the `pgcrypto` and `pg_trgm` contrib extensions, both bundled
with the standard image. The recommended image is `postgres:18`.

**NATS 2.10+** with JetStream enabled. NATS handles pub/sub messaging for
real-time events and persistent job queues for asynchronous processing.
JetStream must be enabled with sufficient storage allocation: the default
configuration uses 1 GB of memory store and 10 GB of file store.

**An S3-compatible object store** for first-party blobs: uploaded files,
detection audits, redacted output, and avatars. The compose files use
[RustFS](https://rustfs.com) (MinIO-compatible, Apache-2.0); AWS S3 or any
S3-compatible service (MinIO, Cloudflare R2, …) works by pointing `S3_ENDPOINT`
at it. The configured `S3_BUCKET` must exist before the server starts, so the
compose files provision it with a one-shot init container.

## Quick Start

### Development (infrastructure only)

Start PostgreSQL, NATS, and RustFS for local development:

```bash
docker compose -f compose.yaml up -d
```

This starts the services with development defaults (`postgres:postgres`
credentials, JetStream enabled, RustFS with `rustfsadmin` credentials and the
`nvisy-dev` bucket auto-created). Then generate configuration and run the server
locally:

```bash
make generate-all   # .env, keys, migrations
cargo run --features dotenv --bin nvisy-cli
```

#### Optional: inference services (NER, OCR, STT)

Three bento inference services sit behind compose profiles, each published on a
localhost-only port: NER (`elide-ner`, GLiNER2 PII) on 3200, OCR (`elide-ocr`,
OnnxTR) on 3201, and STT (`elide-stt`, faster-whisper) on 3202. `make run NER=1
OCR=1 STT=1` (any subset) brings up the matching profiles and runs the server
with an engine config generated by `scripts/gen-engine-config.sh` from the enabled
services, so it always matches the running stack and its ports.

Each image carries no weights: a one-shot `*-init` warmer downloads the model
into its own cache volume (`ner_cache`, `ocr_cache`, `stt_cache`) on first
start, then the service runs non-root against the cache read-only. Override with
`ELIDE_NER_MODEL`, `ELIDE_OCR_DETECTION` and `ELIDE_OCR_RECOGNITION`,
`ELIDE_STT_MODEL`, `ELIDE_{NER,OCR,STT}_PORT`, or `ELIDE_VERSION`. The service
definitions live in `compose.inference.yaml`, shared with the production stack. STT
diarization is off by default (gated model); enable with `ELIDE_STT_DIARIZE=true`
and `ELIDE_STT_HF_TOKEN`.

The API documentation is available at:

- Scalar UI: `http://localhost:8080/api/scalar`
- OpenAPI JSON: `http://localhost:8080/api/openapi.json`

### Production

Run these from the `docker/` directory. Every command passes
`-f compose.prod.yaml`; without it, compose starts the development stack.

1. Choose which detection models to run. Without them only the built-in pattern
   recognizers run: no named-entity recognition, no OCR, and no speech-to-text.
   Each is a compose profile, `ner`, `ocr`, or `stt`; list the ones you want:

   ```bash
   export COMPOSE_PROFILES=ner,ocr,stt   # any subset, or empty for none
   ```

   Compose reads `COMPOSE_PROFILES` on every command, so the steps below need no
   `--profile` flags. Put it in `docker/.env` (step 3) to keep it.

2. Put the server's key files and engine config in the folder mounted read-only
   at `/etc/nvisy`: `docker/config/`, or the one `NVISY_CONFIG_DIR` names.

   For a **new** deployment, generate the keys there:

   ```bash
   config="${NVISY_CONFIG_DIR:-config}"
   mkdir -p "$config"
   (cd .. && make generate-keys) && mv ../private.pem ../public.pem ../encryption.key "$config/"
   cp engine.example.toml "$config/engine.toml"
   sudo chown -R 1000:1000 "$config"           # the image runs as uid 1000
   ```

   Then edit `engine.toml` before the server first starts, since it reads the
   file only at startup. Its NER, OCR, and STT entries point at the services'
   private-network URLs already; delete the entries for any model you did not
   choose in step 1. Its LLM recognizer is commented out, since it sends
   document text to the provider; uncomment it and set a real key to use one.

   For an **existing** deployment, keep the keys you have and never regenerate
   them: `make generate-keys` replaces the files, and a new `encryption.key`
   cannot decrypt anything written with the old one. Back up the config folder
   with the database.

3. Create `docker/.env` with the values compose requires. Don't copy the
   repository's `.env.example`: its key paths point at the working directory
   and would override the `/etc/nvisy` defaults.

   ```bash
   VERSION=0.1.0-rc.1        # a release published on ghcr.io, or `local` with --build
   COMPOSE_PROFILES=ner,ocr,stt
   POSTGRES_PASSWORD=...
   NATS_TOKEN=...
   S3_ACCESS_KEY_ID=...
   S3_SECRET_ACCESS_KEY=...
   CORS_ORIGINS=https://app.example.com
   ```

4. Start the stack, pulling the `VERSION` image:

   ```bash
   docker compose -f compose.prod.yaml up -d
   ```

   Or build the server image from this checkout instead (with `VERSION=local`):

   ```bash
   docker compose -f compose.prod.yaml up -d --build
   ```

   The first start downloads each chosen model into a cache volume; later
   starts reuse it, and the server waits for every chosen model to be ready.

   After changing `engine.toml` or `COMPOSE_PROFILES` later, apply it with
   `docker compose -f compose.prod.yaml up -d` and restart the server
   (`docker compose -f compose.prod.yaml restart server`).

The production compose file starts every service on a private bridge network.
The server waits for the PostgreSQL, NATS, and RustFS health checks to pass,
and for the bucket-provisioning init container to finish, before starting.

## Services

| Service    | Port(s)    | Description                      |
| ---------- | ---------- | -------------------------------- |
| PostgreSQL | 5432       | Primary database                 |
| NATS       | 4222, 8222 | Message queue (JetStream)        |
| RustFS     | 9000, 9001 | S3-compatible blob store         |
| Server     | 8080       | Nvisy API                        |

## Configuration

All configuration is provided through environment variables. See
[`.env.example`](../.env.example) at the repository root for a complete
reference with defaults and descriptions.

Two settings depend on the deployment topology and default to the
directly-exposed case:

- `CLIENT_IP_SOURCE` decides where the caller's IP is read from for audit and
  security records. It defaults to `ConnectInfo` (the TCP peer). Behind a reverse
  proxy or load balancer that sets a forwarding header, set it to the matching
  source (e.g. `RightmostXForwardedFor`), or the recorded IP is the proxy's.
- `COOKIE_SECURE` defaults to `true` (session cookies are HTTPS-only). Set it to
  `false` only for local HTTP development.

## Key Generation

The server requires an Ed25519 keypair for JWT signing and a 32-byte key for
connection credential encryption. Generate both with:

```bash
make generate-keys
```

This produces three files: `private.pem`, `public.pem`, and `encryption.key`. In
production, store these securely. The production compose file reads them from
its mounted config folder (see [Production](#production)).

## Container Image

The Dockerfile uses a multi-stage build:

1. **Planner:** generates a dependency recipe with cargo-chef
2. **Builder:** builds dependencies from the recipe (cached), then builds the
   server binary and strips it
3. **Runtime:** minimal Debian image with only the binary and runtime libraries

The runtime image runs as a non-root user (`nvisy`, UID 1000) and includes a
health check against `/health/ready`. The binary is `nvisy-cli`.

## NATS Configuration

The default NATS configuration (`nats/nats.conf`) enables JetStream with:

- 1 GB memory store for high-throughput streams
- 10 GB file store for persistent data
- 8 MB maximum payload size

Adjust these values based on expected workload. The memory store is used for
ephemeral streams; the file store is used for durable subscriptions and job
queues.

## Encryption at Rest

The server encrypts sensitive payloads at the application layer with
XChaCha20-Poly1305 under per-workspace keys before they reach storage: file
bytes, redacted output, analyzed documents, webhook signing secrets, and
policy/context definitions. The blob store only ever receives ciphertext; any
server-side encryption it offers is redundant defense-in-depth. This protects
those payloads even against a live read of the datastore.

For everything else on disk (NATS stream/consumer metadata and KV entries,
Postgres rows, backups), provision the data volumes on **encrypted storage**.
This adds no runtime overhead, keeps key management out of the datastores, and
covers the whole volume.

The persistent volumes to encrypt are `nats_data`, `postgres_data`, and
`rustfs_data`:

- **Cloud:** back the volumes with an encrypted block device (e.g. an encrypted
  EBS volume, or a cloud disk with default SSE enabled), or bind-mount them onto
  an encrypted filesystem.
- **Self-hosted:** place the Docker data root (or a bind mount for these
  volumes) on a LUKS-encrypted partition.

Volume encryption guards against stolen disks, snapshots, and backups. It does
not protect against a compromised running host, which is why the sensitive
payloads above are additionally encrypted at the application layer.

## Health Checks

All services expose health check endpoints:

| Service    | Endpoint                             | Method   |
| ---------- | ------------------------------------ | -------- |
| Server     | `/health/live`, `/health/ready`      | HTTP GET |
| PostgreSQL | `pg_isready`                         | CLI      |
| NATS       | `/healthz` on port 8222              | HTTP GET |
| RustFS     | `/health/ready` on port 9000         | HTTP GET |

The compose files configure health checks with 5-second intervals. The server
depends on PostgreSQL, NATS, and RustFS being healthy before it starts accepting
requests.

## Database Migrations

Migrations are embedded in the server binary and applied automatically on
startup. For manual control:

```bash
make generate-migrations   # Apply and regenerate schema
make clear-migrations      # Revert all (destructive)
```

## Commands

These use the development stack. For production, add `-f compose.prod.yaml` to
each command.

```bash
# Start services
docker compose up -d

# View logs
docker compose logs -f

# Stop services
docker compose down

# Reset data
docker compose down -v
```
